# スクラップビューアー全体設計案

作成日: 2026-10-02  
状態: Tauri移行後の設計案。Tauri＋Svelte＋daisyUIの採用方向は決定済み。依存バージョン、詳細API、本文選択の実機合格は未確定。

## 1. 目的と資料の位置付け

ローカルのMarkdownスクラップを検索・閲覧・タグ編集・Git同期まで一つのデスクトップアプリで扱う。Markdownファイルを原本とし、外部エディターやエージェント、複数PCでの既存の運用を維持する。

本資料は[移行とUI選定のスクラップ](../.scraps/20261002-1402-スクラップビューアーのTauri移行とUI選定.md)を反映し、[旧全体設計案](旧実装プラン/20261002-1108-スクラップビューアー全体設計案.md)を更新したもの。旧案の機能要件を引き継ぎ、表示方式と処理の境界をTauri向けに組み直す。旧計画のegui向け手順はそのまま適用せず、本資料を基に新しい段階別計画を別途作成する。

今回は設計資料の作成のみ。実装、依存追加、性能測定、実機検証は行っていない。

## 2. 前提と決定事項

### 採用方向

- Tauri＋Svelte＋daisyUIを使う。SvelteKitは初期構成に含めない。
- フロントエンドのパッケージ管理にはpnpmを使う。依存の導入は `pnpm install`、スクリプト実行は `pnpm run` を使い、`pnpm-lock.yaml` で依存を固定する。
- Rustが設定・文書解析・検索・タグ保存・Git処理を担当し、画面側が表示・入力・操作要求・結果表示を担当する。
- 見た目は既製の標準スタイルを使い、独自デザインを作り込まない。
- 依存関係と学習量の少なさを重視する。起動速度やメモリが旧方式と同等とは確認されていない。
- タグとスクラップ一覧は同じサイドパネル内で切り替え、本文と合わせて2列構成にする。
- 設定パスは `~/.config/scrap-viwer/config.toml`。指定表記の `scrap-viwer` を維持し、プロジェクト名へ自動補正しない。

### 引き継ぐ要件

タイトル・要約・本文の検索、タグ絞り込み、YAML frontmatterを正本とするタグ追加・削除、MarkdownとGitでの共有を維持する。整形済み本文の範囲選択とコピーを必須条件とし、原文Markdownのコピーで代替しない。Gitは通常の自動マージを許容し、競合解決は外部IDEに任せる。

### 現在の作業ツリー

`Cargo.toml` はRust 2024 editionで依存未追加、`src/main.rs` は起動メッセージだけ。現在の作業ツリーにGUIや文書処理はない。過去のegui検証結果はスクラップと旧詳細計画に記録されている。

旧計画の `tests/fixtures/selection.md` は現在存在しない。検証時に旧版から復元するか、同じ検証条件を含む文書を用意する。

## 3. 初期版の範囲

| 対象 | 設計案 |
| --- | --- |
| 閲覧対象 | 設定した1つのフォルダと配下のMarkdown |
| 一覧 | タイトル、日付、要約、タグ |
| 本文 | 日本語Markdown表示、整形済み本文の選択・コピー |
| リンク・画像 | 対象内Markdownへの相対リンク、外部HTTP/HTTPSリンク、対象内ローカル画像 |
| 検索 | タイトル・要約・本文の部分一致とタグ1つの絞り込み |
| タグ編集 | 既存タグ・新規タグの追加、削除、明示的な保存 |
| 更新 | 起動時読み込み、手動再読み込み、後続段階で変更検知 |
| 同期 | 利用者が開始するコミット・fetch・merge・push |
| 競合 | 状態表示、保存・同期停止、外部IDEへの引き継ぎ |

本文編集、タグの一括変更・統合、複数保管庫、スマートフォン対応、常時自動同期、アプリ内競合解決は初期版の対象外とする案。

## 4. 技術構成と採用条件

| 要素 | 責務・方針 |
| --- | --- |
| Tauri | ウィンドウ、Rustとの通信、権限、配布 |
| Rust | 設定、文書、検索、保存、Git、処理状態の正本 |
| Svelte＋TypeScript | 表示、入力、画面の状態、操作要求 |
| daisyUI＋Tailwind CSS | タブ、入力、ボタン、バッジ等の標準スタイル |
| Vite | フロントエンド開発・静的成果物のビルドの候補 |
| Markdown変換・HTMLサニタイズ | Rust側を第一案とし、ライブラリは未選定 |
| インストール済みGit | 既存の認証環境を利用したGit操作 |

React、Astro、GPUIは初期構成に含めない。daisyUIは見た目の部品であり、検索やタグ編集の動作は別途実装する。実装開始時に互換性を確認してバージョンを選び、Rustは `Cargo.lock`、フロントエンドはpnpmの `pnpm-lock.yaml` で固定する。

### 最初の通過条件

旧egui構成では選択中のスクロールと画面外までの選択維持が不合格だった。TauriではWindowsのWebView2にHTMLを表示し、WebViewの文字選択を使う。ただし方式の決定は合格確認ではない。検索や保存を積み上げる前に次を実機確認する。

- 日本語表示と検索・タグ入力でのIME変換・確定。
- 整形済み本文のドラッグ選択と `Ctrl+C` によるコピー。
- 複数段落・箇条書き・表をまたぐ選択。
- 選択中のホイールスクロール、画面端での自動スクロール、画面外までの選択維持。
- コピー先での日本語・改行・表内容の保持。
- 横長の表・コードの閲覧、相対Markdownリンクの取得。
- 一覧、タブ、タグ件数、処理状態の更新で本文選択が失われないこと。

不合格なら本文DOM・CSS・スクロール領域・WebViewの挙動を調べ、表示構成を再検討する。必須条件を満たすまで後続段階へ進めない。日本語フォントはOS標準とCSS指定から検証し、旧案のフォントファイル読み込みは前提にしない。

## 5. 画面構成

```text
┌───────────────────────────────────────────────────────┐
│ 検索欄                          再読み込み   同期     │
├───────────────────────┬───────────────────────────────┤
│ [スクラップ] [タグ]   │ タイトル・日付                │
│                       │ タグ追加・削除・保存          │
│ スクラップ一覧        │                               │
│ またはタグ一覧        │ Markdown本文                  │
│                       │                               │
├───────────────────────┴───────────────────────────────┤
│ 件数・読み込み状況・同期状態・エラー                  │
└───────────────────────────────────────────────────────┘
```

- サイドパネルは幅を調整でき、本文と独立してスクロールする。
- 初期タブは「スクラップ」。一覧は日付降順で、タイトル・日付・要約・タグを表示する。
- 「タグ」は「すべて」「未分類」とタグ一覧。タグを選ぶと条件を適用し、「スクラップ」へ切り替える案。適用条件と解除操作を一覧上部に表示する。
- タブ切り替えだけでは検索条件や本文を変更せず、各一覧のスクロール位置を維持する。
- 絞り込み対象外になった文書も、別文書を選ぶまで本文を維持し、対象外であることを表示する。
- 検索とタグ条件はAND。検索実行時は「スクラップ」へ切り替える案。
- タグ編集中の文書移動では保存・破棄・移動中止を選べる。終了時も未保存の変更を確認する。
- 空フォルダ、検索結果0件、読み込み失敗を区別する。
- 同期中は二重実行とタグ保存を止め、閲覧・検索を継続する。
- daisyUIの標準部品を使い、配置と本文の可読性に必要なCSSだけを追加する。本文の文字選択を無効にしない。

本文は独立したコンポーネントとし、同じ文書・本文内容ならHTMLを再挿入しない。タグ保存、一覧更新、同期進捗だけで本文DOMを作り直さない。表・コードには必要に応じて横スクロールを設ける。

## 6. 設定ファイル

固定の読み込み先は `~/.config/scrap-viwer/config.toml`。Windowsでもホーム基準で解決し、暗黙にAppDataへ変更しない。

- 起動時に読み込み、初期版の設定変更は再起動で反映する。
- 未作成なら設定パスと記入例を表示し、対象フォルダを推測しない。
- 不正TOML・値の誤りは項目と理由を可能な範囲で表示する。
- 絶対パス、先頭の `~/`、設定ファイルの親ディレクトリ基準の相対パスを許可する案。カレントディレクトリ基準にはしない。
- 環境変数やシェル式は展開しない。設定は端末固有とし、スクラップの同期対象に含めない。

設定例。キー名は設計案。

```toml
[source]
directory = 'E:/note/codex-brainstorm/.scraps'
recursive = true

[git]
enabled = true

[editor]
command = 'zed'
```

`source.directory` は必須、`recursive` の既定値は `true`、`git.enabled` の既定値は `false` とする案。`editor.command` は任意の実行ファイル名またはパスで、文書・リポジトリのパスは別引数で渡す。

Gitルートは表示フォルダから検出し、現在のブランチと設定済みupstreamを使う。表示フォルダとリポジトリ全体を同一視しない。

## 7. データの読み込みと検索

Markdownだけを永続的な原本とし、初期版はDBや永続検索索引を持たない。Rust側で文書ID、パス、元の内容、タイトル、日付、要約、タグ、本文、内容版を保持する。内容版は外部変更検知に使うが、保存時には実ファイルを読み直す。

- タイトルは最初のレベル1見出しを優先し、なければファイル名。
- `date`、`summary`、`tags` は冒頭のYAML frontmatterから取得する。
- frontmatterなしでも閲覧・検索できる。不正YAMLは警告し、原文確認を可能にしてタグ保存を停止する。
- 日付なし・不正日付は日付付き文書の後ろへ置き、パス順で安定化する案。
- ドット付き対象フォルダも読む。`.git` 内部やシンボリックリンクによる循環を探索しない。

検索はRust側のメモリ上の部分一致から始める。対象はタイトル・要約・本文、空文字は全文書に一致。英字の大文字・小文字を区別しない案。日本語の表記揺れ、読み仮名、あいまい検索は初期版で扱わない。

一覧には要約を使い、ヒット箇所の抜粋は後続候補。全文・HTMLは一覧応答に含めず、選択時に取得する。実際の文書数と遅延を測ってから索引や一覧の仮想化を検討する。

## 8. Markdown表示とリンク

Rustでfrontmatterを分離し、MarkdownをHTMLに変換する第一案とする。選択中文書を中心に文書ID・本文内容版で変換結果をキャッシュし、無制限に蓄積しない。

### HTMLの安全性と選択維持

- 生成HTMLはサニタイズし、許可するタグ・属性・URLを限定する。
- 生HTMLは初期版では無効化または文字列表示。script、イベント属性、危険なURLスキームを受け入れない。
- 本文中の記述を任意のTauriコマンドへ直接接続しない。
- 同じ本文の再取得ではDOMを差し替えない。本文変更・文書切り替え時にだけ反映する。
- 文書切り替え時は選択を解除し、原則先頭へ移動する。見出しリンクなら対象見出しへ移動する。
- 見出し、段落、リスト、引用、表、コード、リンク、画像を検証する。コードの色分けは後続候補。

### リンクと画像

- 相対リンク・画像は現在の文書のディレクトリ基準で解決する。
- 対象内Markdownリンクはアプリ内文書切り替えへ接続する。編集中なら通常の移動と同じ確認を通す。
- 親ディレクトリ移動、URLエンコード、日本語パス、見出し断片を処理し、実体のパスが許可範囲内かRust側で確認する。
- 存在しないリンク、対象外ローカルリンク、未対応形式は理由を表示して本文を維持する。
- HTTP/HTTPSは利用者のクリックでOS標準ブラウザーへ渡す。アプリのWebViewを外部サイトへ遷移させない。
- ローカル画像は初期版では対象フォルダ内に限定する案。Tauriの資源提供方式は導入時に選定し、ホームやリポジトリ全体を公開しない。
- 外部画像の自動取得は無効とする案。文書内見出しと画像は個別に導入する。

Tauriの権限設定とCSPは必要な機能だけ許可する。開発時と配布時の資源URLの違いを確認し、本文から任意のファイル取得・コマンド実行・ネットワーク取得を可能にしない。

## 9. タグ編集と保存

画面には編集用の一時タグ案を持ち、「保存」で原本へ反映する。空タグは禁止、前後の空白は除去、完全一致の重複は防ぐ。タグ名の自動統合はしない。

YAML frontmatterの `tags` だけを変更し、本文、他のキー、コメント、改行形式を維持する。YAML全体の単純な再シリアライズで原文を失わない方式を検証して選ぶ。

1. Rust側で文書ID・タグ・操作状態を検証する。
2. 保存直前に読み直し、編集開始時の内容と比較する。
3. 外部変更があれば上書きせず、再読み込みを案内する。
4. 同じディレクトリの一時ファイルへ完成内容を書き込む。
5. Windowsに適した置き換えで保存し、失敗時は元ファイルを残す。
6. 一覧・タグ件数・検索データ・内容版を更新する。本文が同じなら表示DOMは維持する。

frontmatterなしならタグ用frontmatterを追加。不正YAML、複数の `tags` キー、未対応タグ表現は保存を止める。比較から置き換えまでの外部更新は比較だけでは完全に防げないため、同時保存と失敗時の挙動を検証する。

## 10. Git同期

Gitはバックグラウンドで引数を分けて呼び出し、既存の認証環境を使う。認証情報は保存しない。利用者の操作で開始し、clone、新規リポジトリ作成、ブランチ切り替え、強制push、rebaseは初期版で行わない。

### 範囲

- 自動コミットは対象フォルダ配下のMarkdownの追加・変更・削除。画像等は未決定で、初期案では自動コミットしない。
- 同期前に対象変更と未送信コミットを表示する。
- 既存のステージ済み変更、対象外の未コミット変更、進行中merge/rebaseがある場合は停止する案。
- 対象外の未追跡ファイルは追加しない。マージを妨げた場合はエラーを表示する。

コミット範囲を絞ってもpushはブランチの未送信コミット全体を送り、fetch/mergeはリポジトリ全体に作用する。対象外変更を含む未送信コミットはその事実を表示し、フォルダ限定同期とは説明しない。

### 流れ

1. リポジトリ、ブランチ、upstream、作業状態を確認する。
2. 対象変更・未送信コミットを提示し、利用者が同期開始する。
3. 開始時に状態を再検証し、プレビューから変化した場合は再提示する。
4. 対象変更があればコミット。空コミットは作らない。
5. fetchし、取得したupstreamをmerge。早送り可能なら早送り、分岐していれば通常の自動マージを試す。
6. 成功したら明示したupstreamの送信先へpushする。
7. 成否にかかわらず状態を再取得し、作業ツリーが変わったら文書も再読み込みする。

| 状況 | 動作 |
| --- | --- |
| Gitなし、認証・upstream未設定 | 理由を表示し閲覧継続 |
| fetch失敗 | ローカルコミットを保持し再試行可能にする |
| マージ競合 | 同期停止、対象表示、タグ保存停止、外部IDEを案内 |
| push拒否・通信失敗 | ローカル結果を保持し、強制送信せず再試行を案内 |
| 外部IDEで解決 | 状態再確認で進行中操作・未解決競合がなければ制限解除 |

競合中も閲覧を維持し、競合マーカー付き文書は警告付き原文確認を提供する。IDE未設定なら対象パスを表示する。

## 11. 通信と状態管理

```text
Svelteの画面・操作状態
       ↓ 型付き要求       ↑ 結果・状態通知
Tauriコマンド境界（入力検証・操作制御）
       ↓                 ↑
Rustのアプリ状態・サービス
       ↓
設定 / 文書 / 検索 / 保存 / Git
```

Rust側に設定、文書正本、内容版、保存・同期状態を置く。Svelte側には検索入力、タブ、選択ID、スクロール位置、未保存タグ案、本文表示結果を置く。タグ案を保存前に正本へ混ぜない。

### API案

| 操作名案 | 入力 | 結果 |
| --- | --- | --- |
| `load_catalog` / `reload_catalog` | 操作要求 | 一覧、タグ件数、警告、世代 |
| `search_documents` | 検索・タグ条件、要求番号 | 一覧用情報、世代・要求番号 |
| `get_document` | 文書ID | 本文HTML、メタデータ、内容版、警告 |
| `save_tags` | 文書ID、編集開始時の内容版、タグ案 | 保存結果、更新情報 |
| `get_git_status` | 操作要求 | ブランチ、変更・競合・処理状態 |
| `preview_sync` / `start_sync` | 確認要求 / プレビュー識別情報 | 対象確認 / 処理ID |
| `open_external_link` / `open_editor` | URL / 文書ID等の限定指定 | 検証後の外部起動結果 |

名称・型は未確定。JSONで渡せるDTOを使い、Rust内部構造を直接公開しない。文書IDからRust側でパスを解決する。任意パスやシェル文字列を受け付ける汎用APIは作らない。エラーは種別・利用者向け説明・対象情報に分ける。

長時間処理は処理ID付きイベントで進捗を通知する案。開始応答と状態再取得で取りこぼしを補う。Gitや全件読み込みをUI処理で待たず、Rustの重い処理も通信処理を止めないように分離する。

- 検索は短い待ち時間でまとめ、IME変換途中の不要な要求を避ける。
- 検索の要求番号、読み込みの世代番号、文書の内容版で古い応答を排除する。
- 文書取得中に別文書を選んだら、以前の応答を本文へ反映しない。
- 保存と同期はRust側でも排他し、ボタン無効化だけに頼らない。
- 再読み込みで未保存タグ案を消さず、原本変更を通知する。
- 文書状態とGit状態を分け、Gitエラーだけで閲覧不能にしない。
- ファイル監視はイベントをまとめ、自分の保存・同期と調整する。初期段階は手動更新。

### 配置案

| 配置 | 責務 |
| --- | --- |
| `package.json`、`pnpm-lock.yaml` | pnpmによるUI・ビルド依存の管理と固定 |
| `src/main.ts`、`src/App.svelte` | 画面起動、全体配置 |
| `src/lib/components/` | サイドパネル、本文、タグ、状態表示 |
| `src/lib/api.ts`、`types.ts` | Tauri呼び出し、通信型 |
| `src-tauri/Cargo.toml`、Rustのロックファイル | Rust・Tauri依存 |
| `src-tauri/tauri.conf.json`、`capabilities/` | ウィンドウ、資源、権限、配布 |
| `src-tauri/src/main.rs`、`lib.rs` | 起動、登録、初期化 |
| `src-tauri/src/commands.rs`、`app.rs` | 通信境界、状態、操作調整 |
| `src-tauri/src/config.rs` | 設定、パス解決 |
| `src-tauri/src/document.rs`、`catalog.rs` | モデル、解析、収集 |
| `src-tauri/src/markdown.rs` | HTML変換、サニタイズ、リンク |
| `src-tauri/src/search.rs`、`storage.rs`、`git.rs` | 検索、保存、Git |
| `tests/fixtures/` | 閲覧・保存等の検証文書 |

標準的なTauri配置へ移行する案。ルートCargo構成を残すかworkspace化するかは導入時に判断する。最初から空モジュールを作らず、必要な段階で分離する。

## 12. 検証方針

- 閲覧: 開発時とWindows配布ビルドで日本語・IME・選択・コピー・スクロール・本文DOM維持を実機確認。
- 設定・解析: 未作成、不正TOML、相対パス、frontmatterなし、不正YAML。
- HTML・権限: 危険なHTML/URL、対象外リンク・画像、任意パス要求を拒否できること。
- 保存: 本文・未知のキー・コメント・改行の維持、外部更新、書き込み・置き換え失敗で原本を失わないこと。
- 非同期: 連続検索・文書切り替え、古い応答、二重操作、未保存状態での更新。
- Git: テスト用bareリポジトリと2作業コピーで通常同期、自動マージ、競合、送信拒否、再試行、対象範囲を確認。
- 運用: 実文書量で起動・検索・切り替え・メモリを測定し、処理中も画面を操作できること。

Git検証に実際のスクラップリポジトリを使わない。数値性能の目標は未設定であり、大量文書の性能を事前保証しない。

## 13. 実装順序

このファイルと以下の手順番号を指定して、`make-plan` スキルでその手順の詳細プランを作成し、プランに沿って実装する。番号は個別プランの対象を識別する固定番号とし、後から手順を追加する場合も既存番号を振り直さない。

### 実装手順案

1. **Tauriの最小構成**  
   Tauri＋Svelte＋TypeScript＋daisyUIを導入し、Windowsでの起動とRust通信を確認する。

2. **Markdown表示と閲覧方式の検証**  
   HTML変換・サニタイズ・本文表示を用意し、日本語、IME、選択・コピー、画面外までの選択を実機検証する。

3. **設定読み込み**  
   固定パスのTOMLを読み込み、対象フォルダの解決と未設定・不正設定の案内を実装する。

4. **文書収集と解析**  
   Markdownとfrontmatterを解析し、タイトル・日付・要約・タグを一覧用データにまとめる。

5. **2列閲覧画面**  
   切り替え式サイドパネルと本文を配置し、文書切り替えや一覧更新でも本文選択を維持する。

6. **相対リンクとローカル画像**  
   文書間リンク、見出し移動、画像、外部ブラウザー起動を実装し、許可範囲外のアクセスを防ぐ。

7. **本文検索**  
   タイトル・要約・本文の部分一致検索を実装し、IME入力と古い検索結果の扱いを確認する。前提は手順5。

8. **タグ一覧と絞り込み**  
   タグ件数、「すべて」「未分類」、検索とのAND条件、絞り込み解除を実装する。

9. **手動再読み込み**  
   外部で追加・変更・削除した文書を反映し、選択状態と読み込み世代を管理する。

10. **タグ編集の操作**  
    タグの追加・削除、未保存状態、文書移動・終了時の保存確認を実装する。

11. **原文を維持するタグ保存**  
    本文・コメント・未知のキー・改行を維持し、外部変更と保存失敗で原本を失わない保存処理を実装する。

12. **Git状態表示**  
    ブランチ、upstream、変更、競合、進行中操作と、同期できない理由を表示する。

13. **同期対象のプレビュー**  
    対象Markdownと未送信コミットを提示し、同期開始前に状態を再確認する。

14. **Git同期の実行**  
    コミット・fetch・merge・push、進捗表示、排他制御、同期後の再読み込みを実装する。

15. **競合と外部IDEへの引き継ぎ**  
    競合表示、保存・同期の制限、IDE起動、外部解決後の復帰を実装する。

16. **外部変更の検知**  
    ファイル監視を導入し、自分の保存・同期と調整しながら未保存タグ案を維持する。

17. **Windows配布と日常運用確認**  
    配布版で閲覧・保存・同期を確認し、実文書量で性能と残課題を記録する。前提は手順6・16。

原則として直前の手順を前提とする。例外は手順7（手順5）と手順17（手順6・16）。手順2の閲覧検証が不合格なら、表示構成の修正と再検証を先に行う。

### 個別プランの作り方

対象手順の詳細プランは `.plans` に別ファイルで保存し、全体設計案へのリンク、手順番号、対象範囲、前提の実装状況、作業項目、確認方法、完了条件、停止条件を含める。番号は上記リストの番号を使い、詳細プラン内の小さな作業番号とは区別する。

詳細計画では原則1〜2ファイル・50行未満の小さな変更へ分割する。初期構成の生成や依存設定など、この大きさに収まらない作業は理由と検証単位を明記する。作成時点のコードを確認し、全体設計案の未決定事項のうち対象手順に必要なものを具体化する。

依頼例:

```text
.plans/20261002-1408-スクラップビューアー全体設計案.md の
「実装手順案」の手順1を対象に、make-planスキルで詳細プランを作成して。
```

個別プランを作成した後、そのプランを指定して実装を進める。実装・検証後は個別プランに結果と未完了事項を記録し、次の手順の前提を確認する。

## 14. 実装前・各段階で決める事項

| 論点 | 現在の方向・判断方法 |
| --- | --- |
| UI構成 | Tauri＋Svelte＋daisyUI。採用方向は決定 |
| 閲覧合格 | Windows実機で確認するまで未確認 |
| 依存バージョン | 導入時に互換性を確認、双方のロックファイルで固定 |
| Markdown変換・サニタイズ | Rust側を第一案、表・選択・URL制限を検証して選定 |
| 画像提供 | 対象フォルダ内のみ。方式と権限を検証 |
| 対応OS・配布 | 最初はWindows。WebView2の準備・配布形態を確認。他OSは別途 |
| 設定パス | 指定の `scrap-viwer` を維持 |
| 日本語フォント | OS標準とCSSから確認。追加同梱時は配布条件も確認 |
| YAML編集 | 原文書式と未知の情報を維持できる方式 |
| Git関連ファイル | 初期案はMarkdownのみ、画像等は未決定 |
| 外部IDE | 任意の実行ファイル指定、未設定ならパス表示 |
| 性能 | 実文書量で測定して改善を判断 |
