# スクラップビューアー全体設計案

作成日: 2026-10-02  
状態: 設計案。実装手順・技術採用を確定する前の検討資料。

## 1. 目的

ローカルのMarkdownスクラップを、検索・閲覧・タグ編集・Git同期まで一つのデスクトップアプリで扱う。Markdownファイルを原本とし、エージェントや外部エディター、他のPCとの既存の運用を維持する。

本資料は全体の構造と判断点をまとめる。対応する作業計画は[スクラップビューアー段階別実装計画](20261002-1115-スクラップビューアー段階別実装計画.md)を参照する。計画は16の機能単位で構成し、各単位の実装時に小さな変更へ分割する。

## 2. 前提と要件の位置付け

### 今回のユーザー指定

- まず全体設計案として資料を作成する。
- タグとスクラップ一覧は、同じサイドパネル内で切り替えて表示する。本文と合わせて2列構成にする。
- 表示フォルダなどの設定は `~/.config/scrap-viwer/config.toml` に記載する。
- 設定ディレクトリの `scrap-viwer` は指定された表記を使用する。プロジェクト名 `scrap-viewer` とは異なるが、自動で読み替えない。

### 参考資料から引き継ぐ要件案

- PC向けのローカルアプリを中心とする。
- タイトル・要約・本文を検索し、タグで絞り込む。
- 整形済みMarkdown本文の範囲選択とコピーを必須の採用条件にする。
- タグの正本はYAML frontmatterとし、追加・削除に対応する。
- MarkdownとGitによる複数PC間の共有を維持する。
- 通常の自動マージは許容し、競合の解決は外部IDEに任せる。

参考資料中の提案や未決定事項は、今回のユーザー指示として扱わない。本資料でも未確定の設計として区別する。Gitの方針は、古い資料の「早送りのみ」より後の資料の「通常の自動マージを許容」を採用候補とする。

### 現在のプロジェクト

- `Cargo.toml`: Rust 2024 edition、依存クレート未追加。
- `src/main.rs`: 起動メッセージを表示する初期コードのみ。
- `.plans/SPEC.md`: 調査時点では存在しない。
- GUI、設定読み込み、ファイル処理、Git同期は未実装。

## 3. 初期版の範囲

| 対象 | 初期版の設計案 |
| --- | --- |
| 閲覧対象 | 設定した1つのスクラップフォルダと配下のMarkdown |
| 一覧 | タイトル、日付、要約、タグを表示 |
| 本文 | Markdown表示、日本語、範囲選択とコピー |
| リンク・画像 | スクラップ間の相対リンク、外部HTTP/HTTPSリンク、文書基準のローカル画像 |
| 検索 | タイトル・要約・本文の部分一致とタグ絞り込み |
| タグ編集 | 既存タグから追加、新規タグの追加、削除、明示的な保存 |
| 更新 | 起動時読み込み、手動再読み込み、後続段階で変更検知 |
| 同期 | 利用者が開始するコミット・取得・マージ・送信 |

本文編集、タグの一括変更・統合、複数保管庫の切り替え、スマートフォン対応、常時自動同期、アプリ内の競合解決は初期版の対象外とする案。

## 4. 技術構成と採用条件

候補構成は `eframe` + `egui` + `egui_commonmark`。画面とファイル処理をRustで記述し、既存のUI部品を利用する。

| 要素 | 責務 |
| --- | --- |
| eframe | ウィンドウ、描画、OS入力との接続 |
| egui | パネル、一覧、検索入力、タグ操作、状態表示 |
| egui_commonmark | Markdown本文の表示とキャッシュ |
| Rustのアプリ処理 | 設定、文書解析、検索、タグ保存、処理状態の管理 |
| インストール済みGit | ローカルの認証環境を利用したGit操作 |

採用前に、互換性のあるクレートの組み合わせを選び、次の実機検証を行う。個別クレートの最新版同士が互換とは仮定しない。

- 日本語が表示でき、検索欄・タグ入力欄でIMEの変換と確定ができる。
- ドラッグ選択した本文を `Ctrl+C` でコピーできる。
- 複数段落・箇条書き・表をまたぐ選択が用途に合う。
- スクロールを伴う選択ができ、コピー先の日本語と改行が崩れない。
- 横長の表・コードブロックを欠けずに読める。
- 相対リンクの操作をアプリ内の文書切り替えに接続できる。

この検証が不合格なら、検索や同期を積み上げる前に表示方式を再検討する。WebView方式も比較対象に戻し、プレーンテキストのコピーだけで必須条件を満たしたことにはしない。

日本語フォントの供給方法と配布条件は別途決定する。まず設定したフォントファイルを読み込む案とし、未設定時のOSフォント探索や同梱の可否を検証する。

## 5. 画面構成

左側に切り替え式のサイドパネル、右側に本文を配置する。サイドパネル上部の「スクラップ」「タグ」で表示を切り替える。本文はどちらの表示でも維持する。

```text
┌─────────────────────────────────────────────────────────┐
│ 検索欄                         再読み込み    同期        │
├────────────────────────┬────────────────────────────────┤
│ [スクラップ] [タグ]    │ 選択中の文書                   │
│                        │ タイトル・日付                 │
│ スクラップ一覧         │ タグ追加・削除・保存           │
│ またはタグ一覧         │                                │
│                        │ Markdown本文                   │
│                        │                                │
├────────────────────────┴────────────────────────────────┤
│ 件数・読み込み状況・同期状態・エラー                    │
└─────────────────────────────────────────────────────────┘
```

- サイドパネルの幅を調整でき、本文とサイドパネルは独立してスクロールできる。
- 初期表示は「スクラップ」とする案。一覧は日付の降順とし、タイトル・日付・要約・タグを表示する。日付がない文書の扱いは後述する。
- 「タグ」では「すべて」「未分類」とタグ一覧を表示する。
- タグを選ぶと条件を適用し、「スクラップ」へ切り替えて該当する文書を表示する案。選択中のタグと解除操作をスクラップ一覧の上部に表示する。
- タブの切り替えだけでは検索条件や選択中の文書を変更しない。各一覧のスクロール位置も保持する。
- タグで絞り込んだ結果に選択中の文書が含まれなくても、別の文書を選ぶまでは本文を維持し、「表示中の文書は絞り込み対象外」と案内する。
- 検索とタグ条件は同時に適用する。初期版はタグ1つでの絞り込みとする案。
- 検索を実行したときは「スクラップ」へ切り替えて結果を表示する案。
- タグ編集中に別文書へ移る場合は、保存・破棄・移動中止を選べる。
- 空フォルダ、検索結果0件、読み込み失敗を別々に表示する。
- 同期中は二重実行とタグ保存を止める。閲覧と検索は継続できる。
- 競合時は対象ファイルとIDEでの解決方法を表示する。起動コマンド未設定ならパスを表示する。

## 6. 設定ファイル

### 保存先と読み込み

固定の読み込み先は `~/.config/scrap-viwer/config.toml`。Windowsでもホームディレクトリを基準に解決し、暗黙にAppDataへ変更しない。

- アプリ起動時に読み込む。初期版では設定変更の反映はアプリ再起動とする。
- 未作成なら設定パスと記入例を表示し、対象フォルダを推測して読み始めない。
- TOMLの構文・値の誤りは、分かる範囲で項目と理由を表示する。
- パスは絶対パス、先頭の `~/`、設定ファイルの親ディレクトリ基準の相対パスを許可する案。
- カレントディレクトリを基準にしない。環境変数やシェル式の展開は行わない。
- 設定ファイルは端末固有とし、スクラップのGit同期対象に含めない。

### 設定例（キー名は設計案）

```toml
[source]
directory = 'E:/note/codex-brainstorm/.scraps'
recursive = true

[appearance]
# 必要に応じて端末内の日本語フォントを指定する
# japanese_font = 'C:/path/to/japanese-font.ttf'

[git]
enabled = true

[editor]
command = 'zed'
```

`source.directory` は必須。`recursive` は既定値を `true`、`git.enabled` は安全に試せるよう既定値を `false` とする案。`editor.command` は任意とし、実行ファイル名またはパスだけを受け取り、文書やリポジトリのパスを別引数で渡す。

Gitのルートは表示フォルダから検出し、現在のブランチと設定済みupstreamを利用する。表示フォルダとリポジトリ全体を同一視しない。

## 7. データの読み込みと検索

### 原本とメモリ上のデータ

Markdownファイルだけを永続的な原本とする。初期版ではデータベースや永続検索索引を持たない。

文書ごとに、パス、元のファイル内容、タイトル、日付、要約、タグ、本文、読み込み時の内容識別情報を保持する。元の内容はタグ保存時の外部変更検知にも利用する。

- タイトルは最初のレベル1見出しを優先し、なければファイル名を使用する。
- `date`、`summary`、`tags` は冒頭のYAML frontmatterから取得する。
- frontmatterのない文書も閲覧・検索できる。
- 不正なfrontmatterは警告し、その文書のタグ保存を停止する。原文は確認できるようにする。
- 日付なし・不正な日付は日付付き文書の後ろに配置し、パス順で安定化する案。
- `.scraps` のようなドット付きの対象フォルダも読み込む。`.git` 内部やシンボリックリンクによる循環を探索しない。

### 検索

最初はメモリ上の部分一致検索とする。検索対象はタイトル・要約・本文で、タグ条件との組み合わせはANDとする。空の検索文字列は全文書に一致する。

英字の大文字・小文字を区別しない案とし、日本語の表記揺れ、読み仮名、あいまい検索は初期版で扱わない。一覧には要約を表示し、ヒット箇所の抜粋は後続の改善候補とする。

文書数と操作遅延を測ってから索引方式を見直す。大量文書への性能を事前に保証しない。

## 8. Markdown表示とリンク

- frontmatterを分離し、本文をMarkdownとして表示する。
- 表示対象は原則として選択中の文書だけとし、表示キャッシュを使う。
- 相対リンクと画像は、現在の文書が置かれたディレクトリを基準に解決する。
- 閲覧対象内のMarkdownへのリンクは、アプリ内で文書を切り替える。
- 存在しないリンクは理由を表示し、選択中の文書を維持する。
- 閲覧対象外のローカルリンクや未対応の形式は、自動で取り込まず案内を表示する。
- HTTP/HTTPSリンクはOSの標準ブラウザーへ渡す。
- 文書内見出しへの移動、ローカル画像、コードの色分けは小さく分けて導入する。
- 外部画像の自動取得は初期版では無効とする案。必要性を確認して追加する。

## 9. タグ編集と保存

操作中のタグは編集用の一時状態に保持し、「保存」で文書へ反映する。空タグは禁止し、前後の空白を除き、完全一致の重複を防ぐ。タグ名の自動統合はしない。

保存ではYAML frontmatterの `tags` だけを変更する。本文、他のキー、改行形式を維持する。YAML全体の単純な再シリアライズでコメントや未知の項目を失わない方式を、サンプル文書で検証してから採用する。

1. 保存直前にファイルを読み直し、編集開始時の内容と比較する。
2. 外部変更があれば上書きせず、再読み込みを案内する。
3. 元ファイルと同じディレクトリに一時ファイルを作り、完成した内容を書き込む。
4. 対象OSに適した置き換え方法で保存し、失敗時は元ファイルを残す。
5. 成功後に一覧・タグ件数・検索用データを更新する。

frontmatterがない文書にはタグ用のfrontmatterを追加する。不正なYAML、複数の `tags` キー、未対応のタグ表現は、勝手に修復せず保存を止める。

保存直前の比較と置き換えの間に別プロセスが更新する競合は、比較だけでは完全に防げない。外部エディターとの同時保存を含め、置き換え方法と検知の限界を実装時に検証する。

## 10. Git同期

### 基本方針

Gitコマンドをバックグラウンドで実行し、既存の認証環境を利用する。アプリ内に認証情報を保存しない。シェル文字列の組み立てを避け、引数を分けて呼び出す。

同期は利用者のボタン操作で開始する。リポジトリの新規作成・clone・ブランチ切り替え・強制push・rebaseは初期版では行わない。

### 対象範囲の提案

- 自動コミット対象は、設定したスクラップフォルダ配下のMarkdownの追加・変更・削除とする。
- 画像などの関連ファイルも同期するかは未決定。初期案では自動コミットしない。
- 同期前に対象ファイルと対象範囲を表示する。
- 既存のステージ済み変更、対象外の未コミット変更、進行中のmerge/rebase等がある場合は停止する案。
- 対象外の未追跡ファイルは勝手に追加しない。マージを妨げる場合はGitのエラーを表示する。

コミット対象を限定しても、pushは現在のブランチの未送信コミット全体を送る。fetch/mergeもリポジトリ全体に作用する。このため、未送信コミットに対象外の変更がある場合はその事実を表示し、フォルダ限定の同期とは説明しない。

### 同期の流れ

1. リポジトリ、現在のブランチ、upstream、作業状態を確認する。
2. 対象変更と未送信コミットを表示し、同期を開始する。
3. 対象変更があればコミットする。変更がなければ空コミットを作らない。
4. リモートの変更をfetchする。
5. 取得したupstreamをmergeする。早送り可能なら早送りし、履歴が分岐していれば通常の自動マージを試みる。
6. 成功したら、明示したupstreamの送信先へpushする。
7. 成否にかかわらずGit状態を再取得する。作業ツリーが変わった場合は文書一覧も再読み込みする。

### エラーと競合

| 状況 | 動作 |
| --- | --- |
| Gitがない、認証やupstreamが未設定 | 理由を表示し、閲覧は継続 |
| fetch失敗 | ローカルコミットを保持し、再試行可能にする |
| マージ競合 | 同期を停止し、競合ファイルを表示。タグ編集も停止 |
| push失敗・他端末からの先行push | ローカルの結果を保持し、強制送信せず再試行を案内 |
| 外部IDEで解決済み | 状態を再確認し、進行中操作と未解決競合がなければ制限を解除 |

競合解決中も閲覧を維持する。競合マーカーを含む文書は、通常表示が成功したように扱わず、警告付きで原文を確認できるようにする。

## 11. 処理の分離と状態管理

```text
画面 → アプリ状態・操作要求 → ファイル処理 / 検索 / Git
  ↑                               ↓
  └──────── 処理結果の受信 ────────┘
```

画面描画の中でGitや全件読み込みを完了まで待たない。バックグラウンド処理から結果を受け取り、必要なときに画面を更新する。

状態は「読み込み中」「閲覧可能」「タグ編集中」「同期中」「競合中」「処理失敗」などを明示する。文書の状態と同期の状態を分け、Gitエラーだけで閲覧不能にならないようにする。

手動更新・変更検知・同期後の再読み込みには世代番号を付け、古い結果で新しい状態を上書きしない。ファイル監視は連続イベントをまとめ、自分の保存操作と競合しないようにする。初期段階は手動更新から始める。

### 想定モジュール

| ファイル案 | 責務 |
| --- | --- |
| `src/main.rs` | 起動と初期化 |
| `src/app.rs` | アプリ状態、操作要求、結果反映 |
| `src/config.rs` | TOML設定とパス解決 |
| `src/document.rs` | 文書モデルとfrontmatter解析 |
| `src/catalog.rs` | 文書収集と一覧データ |
| `src/search.rs` | 検索とタグ絞り込み |
| `src/storage.rs` | タグ保存と外部変更検知 |
| `src/git.rs` | Git実行と状態判定 |
| `src/ui.rs` | 画面の描画 |

これは責務の見取り図であり、最初から空のモジュールをすべて用意する指示ではない。必要になった段階で分離する。

## 12. 検証方針

- GUI採用判断: 日本語、IME、選択・コピー、表、コード、スクロールを実機で確認する。
- 設定・解析: 設定未作成、不正TOML、相対パス、frontmatterなし、不正YAMLを確認する。
- 保存: 本文・未知のメタデータ・改行を維持し、外部更新や書き込み失敗で原本を失わないことを確認する。
- Git: テスト用のローカルbareリポジトリと2つの作業コピーで、通常同期、自動マージ、競合、送信拒否、再試行を確認する。
- 操作性: 実際の文書量で起動・検索・文書切り替えを測り、処理中も画面を操作できることを確認する。

Gitの検証には実際のスクラップリポジトリを使用しない。

## 13. 実装に進む際の順序

1. GUIとMarkdown表示の採用検証。
2. 設定読み込みと対象フォルダの検証。
3. 文書解析と、タグ・スクラップ一覧を切り替えるサイドパネル付きの2列閲覧画面。
4. 相対リンク・検索・タグ絞り込み・再読み込み。
5. タグ編集と原文を維持する保存。
6. Git状態の表示、同期処理、競合からの復帰。
7. 外部変更の検知と日常運用の確認。

これは7つの設計上の段階であり、ガイド付き実装のステップ数ではない。詳細計画では各段階を原則1〜2ファイル・50行未満の小さな変更に分割し、目的・確認方法・停止条件を付ける。

## 14. 実装前に決める事項

| 論点 | 現在の提案・判断方法 |
| --- | --- |
| GUI採用 | Markdown選択・コピーの実機検証後に確定 |
| 対応OS | 最初は現在のWindows環境。他のPCのOSは確認が必要 |
| 対象フォルダ数 | 初期版は1つ |
| 設定パスの表記 | 指定どおり `scrap-viwer` を維持 |
| 日本語フォント | 端末内フォントの指定から検証し、探索・同梱を判断 |
| Gitのコミット範囲 | 対象フォルダ内Markdownを提案。画像の扱いは未決定 |
| タグのYAML編集 | 元の書式を維持できる方式を検証して選定 |
| 外部IDE | 任意の実行ファイル指定。未設定時はパスを案内 |
| 外部画像 | 初期版は自動取得しない案 |
